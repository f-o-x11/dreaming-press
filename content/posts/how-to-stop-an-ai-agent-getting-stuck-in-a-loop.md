Anyone who has run an autonomous agent for real has watched it happen: the model calls a tool, gets a result it doesn't like, calls the same tool with the same arguments, gets the same result, and does it again — a dozen times, a hundred, until something kills the run. It is the most common failure mode in production agents, and the standard defense against it is almost always the wrong tool for the job.

## The cap is a backstop, not a fix

The reflex is to add a ceiling. LangGraph makes this concrete: it ships a `recursion_limit` set to **25**, and when a run crosses it you get a [`GraphRecursionError`](https://docs.langchain.com/oss/python/langgraph/errors/GRAPH_RECURSION_LIMIT). Frameworks call it a "max iterations" or "max turns," but it is the same idea — a hard number of steps after which the agent stops.

Keep that ceiling. But be honest about what it does. It fires *after* the agent has already spent every step up to the cap, and every step cost an inference pass and its tokens. A recursion limit doesn't prevent the loop; it caps how expensive the loop is allowed to get before it crashes your run instead of finishing your task. As a cost backstop it's essential — it belongs in the same category as [enforcing a token budget on the agent](/posts/how-to-enforce-a-token-budget-on-an-ai-agent), a limit that protects your bill rather than your outcome. As your primary loop defense, it's a smoke detector wired to go off only once the house is gone.

>> The recursion limit is not loop protection. It is a receipt for the loop, printed after the fact.

## No-progress detection, done wrong

The real technique is *no-progress detection*: watch the agent's recent actions and stop when it stops advancing. The first-pass implementation everyone writes is action deduplication — hash each `(tool, args)` call, keep the last few in state, and if the same call repeats within the window, break the loop. The [LangChain issue tracking this](https://github.com/langchain-ai/langchain/issues/36139) frames it exactly that way; [Hermes-agent's loop guard](https://github.com/NousResearch/hermes-agent/issues/481) reaches for SHA-256 pattern detection over the tool-call history.

And it works right up until it fires on something legitimate. An agent polling a job's status calls `get_status(job_id)` with identical arguments on purpose — that's not a loop, that's the correct way to wait for a result. Naive `(tool, args)` matching flags it as stuck and aborts a run that was doing precisely what it should.

## The distinction that actually holds: the result

The fix the stronger 2026 implementations converged on is *result-aware* detection. A loop isn't "same tool, same args." A loop is **same tool, same args, same result**. If the output changed, the agent learned something and made progress — let it continue. Only an identical `(tool, args, result)` triple, repeated within a window, is a genuine stall. Same input with a different output is exactly the signal that separates real polling from a real loop, and it's what keeps [observability vendors' loop alerts](https://www.getmaxim.ai/articles/troubleshooting-agent-loops-patterns-alerts-safe-fallbacks-and-tool-governance-using-maxim-ai/) from crying wolf on every retry cluster.

When you do catch a stall, don't just abort — the cheapest recovery is to inject a message into the agent's context telling it that this exact action already ran with this exact result, and it must try a different approach. Half the time the model simply hadn't noticed it was repeating itself.

## The loop you should have prevented upstream

Here is the part almost every "how to stop agent loops" guide misses. Most loops are not the agent malfunctioning. Most loops are the agent behaving *correctly* given a bad observation.

Consider a tool that fails and returns `Error: request failed`. To the model, that string carries no information about *why* it failed or whether retrying might help — so retrying is a perfectly reasonable move, and it will keep being reasonable every time it sees the same empty error. The agent isn't stuck in a loop; your tool is feeding it a loop. The [reasoning loops that waste tokens](https://dev.to/aws/how-to-prevent-ai-agent-reasoning-loops-from-wasting-tokens-2652) most often trace back to observations the model can't act on: opaque errors, empty results that look like transient failures, and state changes the agent can't see. It's the same root cause behind so many of the ways [AI agents fail in production](/posts/why-ai-agents-fail-in-production) — the model is only ever as good as what you let it observe.

Which means the highest-leverage fix isn't in the loop at all. Return specific, actionable errors — *what* failed, *why*, and *what to try next*. Make success and failure unambiguous in the observation. Give the agent a domain-aware way to know it's done. An [agent's plan–act–observe cycle](https://blogs.oracle.com/developers/what-is-the-ai-agent-loop-the-core-architecture-behind-autonomous-ai-systems) is only as stable as the "observe" step, and that step is entirely under your control.

So build all three layers, in order of how much work they save you: fix your observations first, add result-aware no-progress detection second, and keep the hard cap last, as the seatbelt you hope never to test. The cap catches the loops you failed to prevent. The other two are how you stop failing to prevent them.
