The fastest way to start an argument in an agent-infrastructure channel this year is to ask a question that sounded settled in 2024: does your agent actually need a vector database?

For two years the answer was reflexive. Memory meant embeddings; embeddings meant a vector store; you reached for Pinecone or Qdrant or Weaviate the way you reach for Postgres, without deliberating. Then, within a few weeks of each other, two of the most-discussed memory releases of 2026 shipped with the vector database deliberately left out — and not from hobbyists. A Google senior product manager, [Shubham Saboo, open-sourced an "Always On Memory Agent"](https://venturebeat.com/orchestration/google-pm-open-sources-always-on-memory-agent-ditching-vector-databases-for) on the official Google Cloud Platform GitHub. Its README does not hedge:

>> "No vector database. No embeddings. Just an LLM that reads, thinks, and writes structured memory."

It stores its memories as structured rows in **SQLite**, ingests continuously, and runs a background consolidation pass every 30 minutes. Anthropic, separately, shipped a [memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) that is even more mundane under the hood: a directory of plain files that Claude creates, reads, updates, and deletes with bash-style commands, running entirely client-side on storage the developer owns. No index. No cosine anything.

It would be easy to read this as a fashion swing — embeddings were overhyped, now files are cool. That reading misses the actual lesson, which is more useful and more permanent.

## Most agent memory was never a similarity problem

Vector search is genuinely excellent at one thing: finding semantically similar passages inside a large body of text *you did not write*. Point it at a documentation set, a support-ticket archive, a corpus of PDFs, and ask "what's relevant to this question," and approximate nearest-neighbor over embeddings is exactly the right instrument. That is retrieval-augmented generation, and nothing here dents it.

But look at what an agent's own memory actually contains. The user's name and time zone. Their stated preferences. The status of the task you're three steps into. The decision you made last turn and why. A running list of what's been tried. This data has a completely different shape from a document corpus: it is *small*, it is *self-authored* — the agent wrote it, so it doesn't need to rediscover it by semantic search — and above all it is *mutable*. Facts change. Tasks complete. Preferences get revised.

Cosine similarity has no answer for mutation. If a user changes their shipping address, you do not want to retrieve whichever stored vector is *closest* to the new one — you want to overwrite the old fact and be done. Similarity search can find something that resembles a memory; it cannot update a memory, and it cannot cleanly delete one. Those are database operations. We spent two years forcing bookkeeping — exact keys, recency, in-place edits — through an engine built for fuzzy recall, and mostly got away with it because nothing better was self-serve.

## What changed is the LLM, not the storage

The reason files and SQLite are suddenly viable as the *primary* store is that the model got good enough to be its own librarian. Anthropic's [context-engineering guidance](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) is explicit about the move: keep memory *outside* the context window and let the model query it with `head`, `tail`, and targeted reads, pulling in only what a given step needs rather than stuffing the whole store through the prompt. Their [context-management release](https://www.anthropic.com/news/context-management) reports that this style of externalized memory plus context editing cut token consumption by **84%** on a 100-turn web-search evaluation — and let runs finish that would otherwise have died of context exhaustion.

That is the unlock. A 2024 model could not be trusted to maintain a coherent SQLite table of facts by writing its own SQL, so you offloaded the judgment to an embedding model and a similarity threshold. A 2026 model can read a folder of notes, decide what's stale, rewrite it, and delete what's dead — the consolidation loop Google's agent runs every half hour is exactly that. The intelligence moved into the reasoning layer, so the storage layer was free to become dumb, legible, and correct.

## Demotion, not death

None of this means ripping out your vector database. It means demoting it from "the memory system" to one tier inside it. The pattern converging across serious 2026 stacks is layered: a small, structured, mutable store for the state the agent touches constantly, and a vector index kept for what it was always good at — open-ended semantic recall over a large corpus the agent didn't author. Mem0 and the embedding-native camp still post the strongest numbers on long-conversation recall benchmarks, and for that workload they earn it. The mistake was never using vectors; it was using them for *everything*, including the mutable state where they're the wrong primitive.

And a caveat worth keeping honest: Google's repo is an MIT-licensed reference implementation, not an enterprise platform — no retention guarantees, no audit workflow, no policy boundaries. "Put it all in SQLite" is not the takeaway. The takeaway is smaller and sturdier: stop defaulting. Pick the store from the shape of the thing you're remembering. Mutable state wants a database it can edit; a static corpus wants an index it can search.

But read them now with the sharper question in hand. Not "which vector database," but "for this memory, a vector database at all?"
