There is a version of protocol design where every release adds a capability, and a rarer version where the important release takes one away. The Model Context Protocol's **2026-07-28 specification** — the release candidate locked on May 21 and dated for July 28 — is the second kind. Its headline moves are subtractions. Protocol-level **sessions are removed**. **Sampling is deprecated**. And the interesting thing is that these two deletions are the same decision wearing two costumes.

## Sessions are gone, and that's the easy half

The old MCP handshake had a shape: a client would `initialize`, the server would confirm, and every subsequent request carried an `Mcp-Session-Id` header that bound the conversation to a specific server holding that session's state. The 2026-07-28 revision deletes all of it. Per **SEP-2567** and **SEP-2575**, the header and the init/initialized handshake are gone.

The payoff is stated plainly in the release notes: a remote MCP server "can now run behind a plain round-robin load balancer" instead of requiring sticky routing. If you have ever tried to scale a stateful protocol horizontally, you know why this matters — sticky sessions are the thing standing between you and just adding more boxes. Take the session out of the connection and every request becomes independent, routable to any replica.

The state didn't vanish; it moved. The spec's pattern is "the model threading an identifier from one tool call to the next" — you hand back an opaque handle from one call and the client passes it into the next. State is now *explicit*, carried in tool arguments, stored in whatever backend you choose. This is the same lesson REST taught a generation ago, arriving in the agent stack: **the protocol should be stateless, and the application should own its state.**

## Sampling is deprecated, and that's the half people will argue about

Sampling was MCP's most ambitious idea. It let a *server* ask the *host* to run a model completion on its behalf — the server borrowed the client's model. That inversion was quietly radical: it meant an MCP server could implement agentic behavior, run its own reasoning step, even drive a loop, without ever holding an API key or picking a model. A server could be genuinely **model-agnostic and self-contained**. You installed it, it worked, and it used whatever model your client already paid for.

As of protocol version 2026-07-28, Sampling is deprecated under the new feature lifecycle policy (**SEP-2577**). Under that policy it survives in the spec for at least twelve more months before it's even eligible for removal — so nothing breaks on July 28 — but the guidance is unambiguous: new implementations should not adopt it, and existing ones should migrate to **direct integration with LLM provider APIs.**

Read that migration path carefully, because it is the whole story. The replacement for "borrow the client's model" is not a cleaner MCP primitive. It is: *stop using MCP for this, and call an LLM yourself.* The protocol is handing the capability back rather than redesigning it.

## The one idea under both changes

Here is the pattern worth carrying out of this release. Sessions were the protocol holding **state** for you. Sampling was the protocol holding **model access** for you. The 2026-07 spec takes back both. What's left is a thinner, more boring MCP: a stateless transport for describing and invoking tools, with the intelligence and the memory deliberately pushed back up into the agent and the client.

That is not a regression. It's a maturation — arriving the same year MCP's [governance moved to a neutral foundation](/posts/who-controls-mcp-agentic-ai-foundation.html) — and it mirrors how every successful protocol ages: toward doing less, more predictably. A dumb pipe scales, load-balances, caches, and survives implementation churn precisely because it refuses to be clever. The spec is also getting *more* rigorous where rigor compounds: full **JSON Schema 2020-12** for tool definitions (SEP-2106), W3C Trace Context in metadata for cross-system tracing (SEP-414), and cache hints (`ttlMs`, `cacheScope`) on list results (SEP-2549). The cleverness is being relocated from the runtime into the contract.

## The bill nobody put on the slide

But subtraction has a cost, and it lands on server authors. The cleanest thing about a Sampling-based server was that it had no API key and no inference bill — it ran on the client's model. Kill Sampling and every server that needs a model now integrates a provider directly. Multiply that across a fleet of installed servers and you get **credential sprawl** (one more place a key lives, one more secret to rotate) and **cost fragmentation** (inference spend scattered across N servers instead of metered at one client). The security and FinOps teams who spent 2025 learning to [attribute agent costs per tenant](/posts/llm-cost-attribution-per-agent-and-tenant.html) just acquired a new surface area.

The authorization changes in the same release read like an anticipation of exactly this. Clients must now validate the token issuer (`iss`) per RFC 9207 (**SEP-2468**), declare an OpenID Connect `application_type` at registration (**SEP-837**), and re-register when a credential's issuing server changes (**SEP-2352**). If servers are going to hold their own credentials, the identity layer around them has to get stricter — and it did. This is the same fault line that produced the [confused-deputy problem in MCP](/posts/mcp-confused-deputy-problem.html): the moment a server acts on someone else's authority, every ambiguity about *whose* authority becomes an exploit.

So the practical read for anyone shipping an MCP server before July 28: **externalize your session state now**, because sticky routing is going away whether you're ready or not; and **treat Sampling as end-of-life**, not because it stops working, but because the protocol just told you where it's going. MCP is choosing to be a smaller thing. The servers that thrive will be the ones that stop asking the protocol to be smart and start owning that themselves.
